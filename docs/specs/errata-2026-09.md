# Errata des specs — 12 septembre 2026

Ce document liste, **par document et par section**, le texte à remplacer
dans les `.docx` de référence (révision du 12/09/2026, commit `b5a81ab`)
pour qu'ils décrivent l'API livrée. Chaque entrée donne le texte actuel, le
texte de remplacement et la source de la décision. Les annexes
« Corrections vX » ajoutées en fin de document par la révision restent
justes ; ce qui suit corrige le **corps** des documents, qui garde souvent
l'ancien contrat, et consigne les décisions prises après la révision (PR #20
à #28). Une fois intégré, `docs/open-questions.md` §F peut être clos.

Conventions : `≠` signale un contrat différent de l'API ; « ajouter » une
section absente. Les extraits markdown de `docs/specs/*.md` (régénérés
depuis les `.docx`) donnent les numéros de ligne cités.

### §2.1 Endpoints auth — 2FA (annexe ligne 95, corps §2.1)

Texte actuel : « À l'ACTIVATION : Returns: { verified: true,
recovery_codes: string[8] } Au LOGIN : Body: { temp_token, totp_code } OU
{ temp_token, recovery_code } ».

Remplacer par : « `POST /auth/2fa/setup` puis `POST /auth/2fa/verify
{ code }` à l'activation : Returns `{ enabled: true, recovery_codes:
string[8] }`. Au login, après un 200 `{ requires_2fa: true, temp_token }` :
`POST /auth/2fa/verify { temp_token, code }` ou `{ temp_token,
recovery_code }`. Un code TOTP accepté ne sert qu'une fois par pas de
30 s (audit LOW-14a) ; cinq échecs consomment le `temp_token` (HIGH-4). »
Source : `docs/backend.md` §3 (auth), `apps/api/src/api/auth/schemas.ts`.

### §3 Vault (ligne 37) ≠

Texte actuel : « signature: base64(Ed25519.sign(SHA256(P1), sk)) … 1.
Ed25519.verify(signature, SHA256(P2 equivalent), ed25519_pk) … POST
/vault/restore Body: { category } ».

Remplacer par :

```
POST /vault/sync
Body: { category: 'accounts'|'messages'|'finances', ts: <entier, ms UTC>,
        payload: base64(P2), signature: base64(Ed25519.sign(SHA256(msg), sk)) }
msg = "relais:vault:v1|" ‖ category ‖ "|" ‖ ts ‖ "|" ‖ P2      (crypto-core syncMessage)
Serveur : |NOW() − ts| ≤ 5 min ET ts strictement croissant par catégorie,
          sinon 409 VAULT_SYNC_STALE ; vérifie la signature ; stocke P2.
Returns: { synced_at, storj_path }

POST /vault/restore { category }
Exige un challenge Ed25519 vérifié dans les 15 minutes
(GET /auth/restore/challenge puis POST /auth/restore/verify), sinon 403 AUTH_RESTORE_REQUIRED.
```

Source : audit MEDIUM-7 et LOW-13, `docs/backend.md` §3.3.

### §4.3 Activation (ligne 49 et annexe ligne 101) ≠

Texte actuel (corps) : `storj_k1_path … share_k1_hash … share_k1_sig` ;
annexe : « shares.kN: { enc, sig, plain_sig } … après vérification
plain_sig, share_kN_plain_hash stocké ».

Remplacer par : « `contacts[].shares.kN = { enc: base64(Si_enc), sig:
Ed25519.sign(SHA256(Si_enc)), plain_hash: SHA256(Si), plain_sig:
Ed25519.sign(plain_hash) }`. Le serveur vérifie `sig` et `plain_sig`,
stocke `Si_enc` (chemin choisi par lui) et **`share_kN_plain_hash`**
seulement ; `plain_sig` n'est pas stockée. Un rôle détenu par moins de N
contacts est refusé (LOW-12). » Retirer `storj_kN_path` et
`share_kN_hash` du corps de la requête. Source : D.3, `docs/backend.md` §3.4.

### §4.4 Vérification annuelle (ligne 52 et annexe ligne 104) ≠

Texte actuel : « POST /transmission/contacts/:id/verify Body: { signature:
Ed25519.sign(SHA256(verify_token), owner_sk) } ».

Remplacer par : « `GET /transmission/contacts/:id/verify-challenge` →
`{ challenge_id, challenge }` (5 min, usage unique) puis `POST
/transmission/contacts/:id/verify { challenge_id, signature }` avec
`signature = Ed25519.sign(SHA256(verify_token ‖ challenge))`. Sans le
challenge, une attestation capturée serait rejouable. » Source : audit
LOW-15b.

### §4 — ajouter

- `GET /transmission/questions` : la bibliothèque des questions secrètes
  (actives, score ≥ `vault.question_min_score`).
- `GET /transmission/config` rend aussi `secret_enc` de chaque contact à

- **`POST /transmission/cancel`** (step-up `cancel_transmission`) : l'owner

### §5 Check-in (ligne 55 et annexe ligne 107) ≠

Texte actuel : « game_token JWT { question_id, answer_hash } » (corps) et

Remplacer par : « `GET /checkin/game` → `{ question_fr, question_en,
game_type, game_token }`, jeton opaque (réponse en Redis, 10 min, usage
unique) ; `POST /checkin/game/answer { game_token, answer }` avec `answer`

### §7 Relay (ligne 61) ≠

Texte actuel : « POST /relay/:token/verify Body: { share_enc:
base64(Si_tmp_enc) } … Returns: { accepted: true, shares_remaining } ».

Remplacer par : « `POST /relay/:token/verify { shares: { k1?, k2?, k3? } }`
(parts en clair, base64, une par rôle détenu) ou `{ failed: true }` (échec
compté). Le serveur compare `SHA256(Si)` à `share_kN_plain_hash` (422
`RELAY_SHARE_INVALID`), scelle les parts dans l'escrow, rend `{ accepted,
answered, needed, unlocked: { k1, k2, k3 } }`. Cinq échecs → 429
`RELAY_TOKEN_EXHAUSTED`, contact bloqué 24 h ; limite 10/min/IP. `GET
/relay/:token/data` rend, une fois N parts réunies, les parts de l'escrow,
P2 et `secret_enc` par rôle, et **`journal`** (carnet sous K2) au porteur de
K2. `POST /relay/:token/confirm` purge tout, carnet compris, quand chaque
contact ayant répondu a confirmé. » Source : B.4, D.3, lot 6,
`docs/backend.md` §3.7.

### §7 — ajouter : l'owner est prévenu

## 2. Specs Techniques v1.3

### §1 Vocabulaire (ligne 18) ≠

« S1…SM | Parts Shamir de Ki. 32 bytes bruts. » → « Parts Shamir de Ki,
**33 octets** : 32 octets de donnée précédés de l'**index de la part**
(abscisse GF(256)), pas d'un « header ». Si_enc = XChaCha20(K_i, S_i). »
Même correction annexe ligne 151 (« 1 byte header GF256 »). Source :
`docs/crypto-core.md` §3.

### §4 Schéma Shamir

Préciser : GF(256) maison (crypto-core), Argon2id INTERACTIVE pour K_i
(MODERATE pour les clés de catégorie), sel de K_i dérivé des
`question_id`, réponses normalisées (minuscules, sans accents, espaces
réduits). Retirer `@noble/ed25519` partout : `libsodium-wrappers-sumo`
seul.

### §5.2 Saisie et chiffrement local (ligne 76) ≠

« P2_i = XChaCha20(Ki, P1_i) … sig = Ed25519.sign(SHA256(P1_i)) » →
« P2 = enveloppe scellée par Ki d'une **liste de fiches chiffrées une à
une** (chaque fiche est un P1 ; `reconstruct` ouvre P2 une fois, l'app
déchiffre chaque fiche). Signature : voir Backend §3 (message
`relais:vault:v1|category|ts|P2`, `ts` entier ms). » L'annexe ligne 157
(« ts = Date.now().toString() ») est à mettre en cohérence : `ts` est un
**entier** dans le corps, concaténé en décimal dans le message.

### §4.3 (annexe ligne 154) secret_enc

`SecretClear { nom, role, message_personnel, email?, phone? }` — `role` =
rôles détenus joints par des virgules (`k1,k2`), champ `phone` (pas
`telephone`). Source : crypto-core.

### §7.3 Step-up

Ajouter `set_key` et `cancel_transmission` (voir Backend §2.3).

### §9 Infrastructure — ajouter

« Les erreurs du stockage objet sont comptées par l'API (sorted set Redis,
15 min) ; le tableau de bord lève `storage_degraded` à partir de cinq
(12/09/2026). » Source : `docs/backend.md` §3 (dashboard).

### §3 — ajouter : restauration sur un nouveau device

`GET /auth/restore/challenge` → signature Ed25519 du challenge →
`POST /auth/restore/verify` (15 min), puis `POST /vault/restore` par
catégorie ; contacts restaurés depuis `secret_enc` (réponses à ressaisir).

### §4.2 Sync vers Storj (annexe ligne 107)

`const ts = Date.now()` (entier, pas chaîne) ; message
`"relais:vault:v1|" + category + "|" + ts + "|"` suivi des octets de P2 ;
un `ts` non croissant est refusé (409 `VAULT_SYNC_STALE`) : l'app sérialise
ses syncs par catégorie (debounce 3 s).

### §5.2 secret_enc (annexe ligne 113)

`telephone` → `phone` ; `rôle` → `role` = rôles joints par des virgules.

### §5 — ajouter : transmission déclenchée à tort

Écran `/transmission/cancel` sous PIN (« Je suis là : annuler la
transmission »), cible du push `transmission_triggered` et du lien des
emails ; appelle `POST /transmission/cancel` (step-up `cancel_transmission`).
Le push n'ouvre que `/checkin`, `/transmission` et `/transmission/cancel`.
Source : `docs/mobile.md` §3.

### §7 Sécurité locale — ajouter

Les réponses secrètes restent sur le device, chiffrées sous K2 (jamais
envoyées) ; la progression du contact vit sous le hachage du token et
expire avec l'accès.

### BO-02 Tickets — ajouter
